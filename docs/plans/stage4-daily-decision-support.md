# 阶段 4 开发计划：每日决策辅助

- 状态：已评审（2026-09-27），按本计划开发
- 日期：2026-09-27
- 关联：ARCHITECTURE.md §5.8–5.13、§7、§8.1、§13、§19（阶段 4）；ADR-005、ADR-007、ADR-008、ADR-009、ADR-010；设计细节见 [docs/design/stage4-app-design.md](../design/stage4-app-design.md)

## 1. 目标与范围

ARCHITECTURE 对阶段 4 的定义：

- **产物**：盘后自动任务、交易建议、审核工作台、CSV/模拟执行和通知。
- **完成标准**：连续运行多个交易日，数据或任务出现异常时，不会生成错误的订单。

**本版要做**：

- 盘后决策作业，带数据质量闸门；
- 交易建议及其解释；
- 人工审核，即批准、修改或拒绝建议；
- 持仓录入与导入；
- 模拟执行；
- 后端 API，以及用户和权限管理；
- PC 网页；
- 安卓 App 框架。

**本版不做**：

- 真实下单和券商接入（阶段 5、6）；
- 盘中实时分析：第一版不做，只保留调研结论，见 §10；
- 离线推送：只做 App 内的通知中心，外部推送渠道放在最后，见 P8。

当前是测试阶段：用户少于 10 人，1 名管理员；通过阿里云 frp 访问，没有域名。

## 3. 总体架构

```text
systemd 用户定时器（工作日 18:17）
  └─ scripts/daily_update.sh
       ├─ quant-data ingest                          （已完成）
       ├─ quant-decision daily                       （P1，新增）
       │    ├─ 数据质量闸门：不通过则不生成建议，只记事件
       │    ├─ 信号：读取最新数据，复用 multifactor 策略
       │    ├─ 目标组合：规则法，以当前真实持仓为起点
       │    ├─ 交易建议：一手取整、涨跌停与停牌检查、费用、原因
       │    ├─ 风险检查：行业/风格暴露、集中度、流动性
       │    └─ 写入业务库，并输出 JSON/CSV/Markdown 决策报告
       └─ backup_data.sh                             （已完成，另加业务库）

FastAPI 后端（systemd 用户服务，只读取算好的结果，不做重计算）
  ├─ 登录、用户、角色、权限、操作审计
  ├─ 市场概览、数据健康、决策、审核、持仓、账户、通知
  └─ 读 market.duckdb（只读）+ 业务库（SQLite → 以后 PostgreSQL）

Caddy（单文件程序）：托管前端静态文件、反向代理 API、TLS
  └─ frp TCP 转发（TLS 在服务器端终止，阿里云中转机看不到明文）

前端（pnpm monorepo，基于 vue-vben-admin v5）
  ├─ apps/web      PC 网页：图表、决策、审核、持仓、用户管理
  ├─ apps/mobile   手机页面（Vant 组件），用 Capacitor 打包成安卓 App
  └─ packages/     共用的 API 客户端、类型、图表组件
```

**原则**：

- 重计算只在盘后批处理里做，Web 进程只读结果，所以接口快，结果可复现。
- 业务规则放在领域模块，路由和页面里不写规则（ARCHITECTURE §5.12）。

## 4. 技术选型

| 部分 | 选择 | 理由 |
|---|---|---|
| 后端 | FastAPI + SQLAlchemy 2 + Alembic + Pydantic | 与现有代码同语言，可直接调用研究模块 |
| 业务库 | SQLite（WAL 模式），以后迁 PostgreSQL | 遵循 ADR-005；不需要 MySQL 或 Redis，无 root 也能跑 |
| 认证 | argon2 密码哈希；短期访问令牌加刷新令牌；登录限流；审计日志 | 规模小，不引入独立的身份认证服务 |
| PC 前端 | vue-vben-admin v5（MIT） | 支持后端下发菜单和权限码，monorepo 结构便于与手机端共用代码 |
| 图表 | ECharts 6 + KLineChart v10（均为 Apache-2.0） | 仪表盘和净值曲线用 ECharts；K 线和技术指标用 KLineChart |
| 手机页面 | Vue 3 + Vant 4（MIT） | 移动端组件，与 PC 端共用 API 客户端 |
| 安卓打包 | Capacitor 8（MIT） | 同一套 Vue 代码，在 Windows 上用 Gradle 构建 APK |
| Web 服务器 | Caddy（单文件程序，普通用户运行） | 托管静态文件、反向代理，内置证书管理 |
| 参考 | RuoYi-Vue3-FastAPI（权限模型）、daily_stock_analysis（决策报告结构）、FreqUI（界面设计，GPL，只参考不复制） | |

以上决定写入 ADR-010（前端、API 与接入）。另补 ADR-008（人工审核与执行边界），这是 ARCHITECTURE §20 预留的。

## 5. 接入与安全（测试阶段）

**访问方式**：

- 在服务器 frpc 上加一个 TCP 转发，并在阿里云安全组开放对应端口。这一步需要管理员操作，我会提供配置片段。
- 浏览器和 App 访问 `https://<阿里云IP>:<端口>`。

**TLS**：

- 没有域名，所以用 Caddy 的内部 CA 签发证书。
- PC 端安装一次这个 CA 证书；App 内置证书指纹（证书固定），不依赖系统信任。
- TLS 在我们的服务器上终止，frp 只转发加密后的字节。

**账号**：

- 管理员首次登录后必须修改密码，可选开启 TOTP 两步验证。
- 连续登录失败会锁定。
- 令牌短期有效；管理员可以踢下线、禁用账号。

**权限**：

- 权限码示例：`decision:view`、`decision:approve`、`position:edit`、`user:manage`。
- 审核操作需要二次确认，并记录操作者、时间、修改前后的内容和原因（ARCHITECTURE §13）。

**环境标识**：界面醒目标注"测试环境"。

## 6. 质量闸门（阶段 4 完成标准的核心）

有以下任一情况时，不生成交易建议，只记录阻断事件和原因：

1. 当天的采集运行不是 `complete`，或者最新交易日不等于预期交易日；
2. 采集之后数据版本变了，比如有人手动重建过；
3. 信号数量或得分分布相对近期历史突变，例如股票池规模偏离超过 20%；
4. 当前持仓过期，最近一次录入或导入早于上一个调仓日，而且期间有过审核通过的交易；
5. 风险检查不通过，例如单票、行业超限，或者一手取整后偏离目标过大。

所有事件都带运行编号、交易日、影响范围和建议动作（ARCHITECTURE §14）。

## 9. 风险

- **免费数据源不稳定**：采集失败时，闸门会阻止生成建议。代价是当天没有建议，而不是给出错误建议。
- **自签名证书**：PC 端需要手动安装 CA。等以后有了域名和备案，可以换成公共证书。
- **业务库用 SQLite**：用户少于 10 人没有问题。进入阶段 5（对账、订单状态同步）之前，迁到 PostgreSQL。
- **手机端推送**：本版只在 App 打开时收消息，离线推送不在本版范围内。
- **个人程序化接入受限（影响阶段 5、6）**：据调研，中证协 2026 年 181 号文（2026-08-28 施行）把券商系统的 API 和外部接入限定给机构，个人现有的 QMT、PTrade 等程序化通道正在清理。这条尚未独立核实，但意味着以后真实下单很可能只能"系统出建议、人工下单"。本版设计本来就是这样，不受影响。

## 10. 盘中实时行情调研结论（P7 输入，2026-09-27）

以下来自调研，价格和政策以官方页面为准，标 (?) 的未能核实。

**免费源**（测试阶段够用）：

| 来源 | 内容 | 单次请求 | 可靠性 |
|---|---|---|---|
| 新浪 `hq.sinajs.cn` | Level-1 快照（5 档）、1/5/15/30/60 分钟线 | 一次 800 只 | 需要带 Referer 头；频繁轮询会被限速 (?) |
| 腾讯 `qt.gtimg.cn` | Level-1 快照（5 档）、分钟线（最多 320 根） | 一次 500 只 | 相对宽松 (?) |
| 东方财富（AKShare 封装） | 全市场列表、逐笔、涨停池、最近 5 天的 1 分钟线 | 一页 100 行，全市场约 60 次请求 | 2025 年起常有封 IP 和验证码 |
| pytdx/mootdx | — | — | 2026-09-10 起被通达信服务器拒绝，不可用 |

- 以上都是交易所约 3 秒一次的 Level-1 快照的转发，另有几秒延迟，没有任何服务保证。
- 按条款，这些数据不得转发或传播。

**付费源**：

- 性价比最高的是 **Tushare Pro**：
  - `rt_k`：一次调用取全市场快照，每月 200 元；
  - `rt_min`：分钟线，每月 1,000 元。
- TickFlow 每月 99–199 元，提供 WebSocket，但成立时间短，数据来源和授权不明，需要先验证。
- Wind、iFinD、Choice 每年数千到数万元，面向机构。

**券商终端**：

- QMT / miniQMT 只支持 Windows，miniQMT 已停止新申请；PTrade 的沙箱不能联网。
- 加上 181 号文的限制，都不适合给 Linux 服务器供数。

**Level-2**：

- 交易所只授权给数据商，个人只能通过行情终端订阅查看（每年约 88–298 元）。
- 个人没有合规的 Level-2 API，本项目不考虑。

**数据量**（全市场约 5,900 只，按每天 240 分钟连续交易估算）：

| 数据 | 每天行数 | 每天 Parquet | 每年 | 实时带宽 |
|---|---|---|---|---|
| 1 分钟线 | 约 140 万 | 20–40 MB | 5–10 GB | 低于 0.1 Mbps |
| Level-1 3 秒快照 | 约 2,400 万 | 0.5–1.5 GB | 120–350 GB | 全市场每 3 秒一轮约 1.3–3 Mbps（gzip 压缩后） |
| Level-2 逐笔 | 2.5 亿–4 亿 | 3–6 GB | 1–1.5 TB | 平均 10–20 Mbps，开盘峰值超过 100 Mbps |

**建议方案**：

- **测试阶段用免费源**：
  - 服务器上只跑一个行情采集进程。持仓加自选股（300 只以内）每 3–5 秒请求一次新浪或腾讯；全市场涨跌分布和涨跌停统计每 30–60 秒一轮，约 8 次批量请求。
  - 结果通过 WebSocket 或 SSE 推给网页和 App，客户端从不直接访问数据源。
  - 分钟线由快照自行合成，另用新浪分钟线补历史，存为 Parquet。
  - 新浪 → 腾讯 → 东方财富逐级降级，失败时退避。
  - 涨跌停价在本地计算，复用 `cn_a_share.json`，其中已包含 2026-07-06 起主板 ST 改为 10% 的规则。
- **需要稳定性时，最便宜的升级**：Tushare `rt_k`，每月 200 元。
- **合规**：把实时行情展示给他人，法律上属于"展示"，需要交易所授权。所以系统要保持登录才能访问、私用、非商业、10 人以内实名用户，App 不公开发布。任何对外公开使用之前，都要通过授权数据商取得数据，或只展示延时行情。
- **版本升级**：AKShare 已到 1.18.97（2026-09-20 发布），项目锁定在 1.18.78。升级要单独做一次回归测试（采集结果对比），不在本版随手升级。

**规则变化提醒**（调研中顺带发现）：2026-07-06 起全部 A 股有 15:05–15:30 的盘后固定价格交易时段。收盘判定时间是 16:00，所以不受影响。

## 11. 讨论结论记录（2026-09-27）

| 议题 | 结论 |
